# Z: Project Foundation

## Goal

Keep CreditSentry reproducible to develop, verify and package through shared project infrastructure with explicit ownership.

## Scope

- In: workspace/toolchain setup, shared configuration infrastructure, quality gates and reusable E2E infrastructure, packaging/release preparation, and project documentation maintenance.
- Out: feature-specific behavior and regression scenarios (A–G), financial privacy/data controls (F), hosted operations and billing (G), and a generic coding-agent or plugin platform.
- Boundary: work belongs to Z only when its deliverable serves the project as a whole and has an observable acceptance criterion. Domain configuration and feature-specific tests stay with their owning feature.
- Authorization: release preparation does not authorize publishing, deployment, workflow edits, new dependencies or other actions requiring explicit approval.

## Acceptance Criteria

```gherkin
Feature: Project Foundation

  @core
  Scenario: R1 — Workspace setup is reproducible
    Given a fresh checkout and the repository's pinned tool versions
    When a developer follows the documented installation and workspace commands
    Then the existing apps and packages resolve and build without undeclared setup steps

  @core
  Scenario: R2 — Shared configuration is validated at its boundary
    Given valid and invalid inputs for shared project configuration
    When applications load that configuration
    Then supported inputs resolve consistently through the established environment gateway and invalid inputs produce actionable errors

  @core
  Scenario: R3 — Shared verification produces repeatable evidence
    Given the documented quality gate and reusable E2E infrastructure
    When verification runs against the selected revision
    Then required checks report failure through nonzero exits and E2E runs leave inspectable artifacts without redefining feature-specific assertions

  @core
  Scenario: R4 — Packaging instructions match the verified deliverable
    Given a local build and its declared runtime requirements
    When a developer follows the documented packaging and local smoke-check steps
    Then the produced deliverable runs as documented without publishing or deploying it

  @core
  Scenario: R5 — Project documentation stays aligned with changes
    Given a change to a shared command configuration boundary or delivery state
    When the change is prepared for review
    Then the owning documentation and affected indexes reflect the observed implementation and distinguish planned behavior from shipped behavior
```
