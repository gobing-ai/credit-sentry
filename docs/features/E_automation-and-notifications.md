# E: Automation and Notifications

## Goal

Run authorized ingestion and minimal-disclosure notification cycles reliably without duplicate records or unchanged alerts.

## Scope

- Deferred in full: one mailbox connector, consent/revocation, bounded schedule/checkpoints, retries and one notification channel after manual workflow validation and scope reconfirmation.
- Out: parser/admission/rule implementations (A/B/C), hosted account/billing ownership (G), generic daemon/agent orchestration platform.
- Boundary: invokes existing domain operations; owns connector progress and delivery attempts, not a second ledger or rule engine.

## Acceptance Criteria

```gherkin
Feature: Automation and Notifications

  @core
  Scenario: R1 — Interrupted authorized polling resumes safely
    Given an authorized connector cycle stops after partial progress
    When the next cycle resumes from the stored checkpoint
    Then no source is silently skipped and existing ledger or finding identities prevent duplication

  @core
  Scenario: R2 — Revocation stops connector access
    Given a user revokes a mailbox connection
    When a scheduled cycle starts
    Then the connector makes no further authorized data reads and reports reconnection requirements

  @core
  Scenario: R3 — Notification retry avoids unchanged alert storms
    Given a delivery failed for a stable finding
    When the bounded retry policy runs and a later audit repeats
    Then delivery state remains visible and unchanged findings do not generate a new alert series

  @core
  Scenario: R4 — Notifications respect disclosure choice
    Given a user selected a minimal notification payload
    When a finding is delivered through the chosen channel
    Then only approved fields leave the local boundary and delivery failures remain inspectable
```
