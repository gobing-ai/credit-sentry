# B: Transaction Records

## Goal

Maintain an exact, persistent, account-scoped ledger whose records can be traced, corrected and safely reprocessed.

## Scope

- In: local accounts, exact money/date validation, reviewed atomic admission, source observations, import/overlap identity, persisted revisions and history queries.
- Out: anomaly interpretation (C), review presentation (D), lifecycle policy (F), multi-tenant cloud ledger and FX conversion.
- Boundary: A owns extraction candidates; B owns every accepted record and the consistency of corrections.

## Acceptance Criteria

```gherkin
Feature: Transaction Records

  @core
  Scenario: R1 — Accepted records persist with exact values
    Given reviewed candidates with validated USD amounts and account identity
    When the user admits the statement and restarts the application
    Then the same exact amounts dates accounts and source links remain queryable

  @core
  Scenario: R2 — Replay preserves legitimate repeated purchases
    Given a statement with two real equal purchases and a known overlapping export
    When the user imports both files and repeats one import
    Then the ledger retains both real purchases and links shared observations without duplicating transactions

  @core
  Scenario: R3 — Correction survives reprocessing
    Given a user-corrected accepted transaction
    When its source is reprocessed
    Then the correction remains authoritative and the transaction revision identifies any newly proposed changes

  @core
  Scenario: R4 — Admission is atomic across interruption
    Given a reviewed statement ready for admission
    When execution is interrupted during its commit
    Then recovery exposes either the complete committed statement or no admitted portion and supports safe retry
```
