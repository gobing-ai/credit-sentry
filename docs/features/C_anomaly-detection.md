# C: Anomaly Detection

## Goal

Identify evidence-backed review candidates from accepted transaction history using reproducible deterministic rules.

## Scope

- In: historical fact derivation, possible duplicates, confirmed recurring price increases, unfamiliar-small-charge advisories, versioned evidence and coverage/insufficient-history outcomes.
- Out: extraction/deduplication (A/B), disposition and presentation (D), notification delivery (E), fraud certification and autonomous financial actions.
- Boundary: operate only on eligible accepted records; ambiguous matches and missing history remain visible.

## Acceptance Criteria

```gherkin
Feature: Anomaly Detection

  @core
  Scenario: R1 — Possible duplicate includes comparison evidence
    Given distinct eligible purchases satisfy the configured duplicate rule
    When an audit evaluates accepted history
    Then one review finding cites the compared records rule version and exact matching parameters

  @core
  Scenario: R2 — Recurring increase requires comparable history
    Given a confirmed monthly series with sufficient comparable prior cycles
    When a higher comparable posted charge is audited
    Then a price-increase candidate includes the baseline current amount and exact delta

  @core
  Scenario: R3 — Missing history is distinguishable from safety
    Given a series lacks comparable cycles or imported history is incomplete
    When the audit evaluates the applicable checks
    Then the report identifies insufficient history or coverage rather than declaring the account safe

  @core
  Scenario: R4 — Rules preserve controls and repeated audit identity
    Given fixtures include refunds payments pending records different accounts and unchanged prior findings
    When the same accepted ledger revision is audited again
    Then ineligible controls are excluded and unchanged findings retain stable evidence identity
```
