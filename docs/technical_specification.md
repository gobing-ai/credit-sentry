## 1. 实际工程基础

当前项目已有 Bun + TypeScript + Biome 工作区、Hono/oRPC 服务端、React/Vite Web、
CLI 客户端以及 config/db/utils 包。代码仍是 planet demo，数据库只有 users 示例，
不存在账单导入、AI 提取、审计规则或多租户能力。实现清单与限制见架构文档 §1。

保留既有工作区边界，不先建立空的 core/parsers/cloud-worker 包，也不把文档中的
示意 API 当作已经存在的依赖。使用现有 Bun SQL/SQLite 路径；未安装的
@gobing-ai/ts-db、better-sqlite3、json-rules-engine 不作为实现前提。

## 2. 方案取舍

| 原提案 | 修订后的方向 | 理由 |
|---|---|---|
| 本地与 Workers/D1 同时建设 | 先验证本地单用户流程，云端重新立项 | 先解决可审计性和恢复能力，避免未经验证的双运行时承诺 |
| Plugin-First Registry / Hooks | 内置窄接口和普通函数，出现第二个真实需求后再抽取 | 不把长尾愿景提前变成平台工程 |
| Day-1 自主 Agent | 有界提取、人工审阅、确定性规则 | 模型输出不具备财务事实或操作授权 |
| json-rules-engine 动态 JSON 规则 | 初期使用版本化 TypeScript 规则 | 历史事实仍需查询/推导；通用规则库不能替代这一部分 |
| 浮点金额、单笔交易视角 | 精确金额、账户/来源/交易分离、历史事实 | 保证比对、重放和证据解释的正确性 |
| 通用 db/env/execute: any 接口 | 按实际 Zod/oRPC 契约和 DB 方法定义边界 | 遵守项目类型与依赖约束，避免不存在的 API |
| 自动调整 Prompt | 显式版本、有限重试和回归评估 | 避免同一来源产生不可解释的结果变化 |
| AES 中间件即零知识 | 记录实际明文处理方和密钥边界 | 普通存储加密与零知识不是同一保证 |
| Public Monorepo + MIT/BSL 已决定 | 保留当前许可证，商业分发待确认 | 避免文档与仓库法律文件冲突 |

Schema 限制不保证提取事实正确；仍需业务验证、来源证据和完整性检查。
[提供方说明](https://developers.openai.com/api/docs/guides/structured-outputs)
明确指出结构化输出仍可能出错。具体提供方、模型、区域与保留策略在实现前再选择，
不把旧模型名称或宣传价格写成长期架构约束。

## 4. 暂缓设计的接入条件

| 能力 | 重启设计前所需证据 |
|---|---|
| Gmail/Outlook 自动摄取 | 手动闭环有效、明确授权范围、撤销/重连/漏采恢复和提供方审核要求；Gmail 范围分类见[官方文档](https://developers.google.com/workspace/gmail/api/auth/scopes) |
| Telegram/Discord/邮件通知 | 先选择一种渠道，确定最小披露、重试去重和交付失败状态；不把发送成功等同用户收到 |
| Cloudflare Workers/D1 | 实际解析负载、资源限制、依赖兼容、迁移/事务语义、身份与租户隔离验证；不承诺直接换驱动无缝运行 |
| SaaS 计费 | 明确身份、租户、权益和成本限额，再设计 webhook 验签、幂等、乱序/重放及对账 |
| AI 财务问答 | 稳定的只读数据查询、账户授权和查询/费用界限；不允许任意 SQL 或自主财务行为 |
| 第三方插件/动态规则 | 内置适配器不足的真实使用证据，以及代码信任、版本和权限设计 |
| FX、扫描/OCR、银行 API | 分别选择支持集、可测语义和输入样本，不以“全球覆盖”替代验收 |

本次评审没有改依赖、API、业务 Schema、工作流、环境文件或部署配置。
